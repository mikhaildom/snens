quickstart.txt — как работает агент snens
========================================

Цикл
----

Один ход = запрос к модели (OpenAI-совместимый /chat/completions со стримом) →
модель отвечает текстом и/или вызовами инструментов → ядро исполняет вызовы →
результаты уезжают обратно в контекст → следующий ход. Цикл заканчивается, когда
модель ответила без вызовов инструментов, или по лимиту ходов (`max_turns`,
дефолт 200 — при достижении ядро просит у модели промежуточный итог, а не падает).

Журнал сессии (`~/.local/share/snens/sessions/<id>.jsonl`) — append-only: сообщения,
вызовы, результаты, ревизии контекста. То, что уезжает провайдеру, — редактируемая
проекция журнала (см. practices.txt, раздел «Контекст»).

Два вшитых инструмента
----------------------

`run` — выполнить shell-команду.
  run <команда> [--cwd каталог]
  Оболочка — из конфига (`shell`), по умолчанию `sh -c` на unix и `cmd /C` на
  Windows. Нужны bash-измы — зови `bash -c '...'` явно.
  Код возврата при `;`-цепочке — от последней команды: хвостовой `which`/`grep`
  красит успешную команду в ошибку. Проверяй `$?` или ставь проверку раньше.
  Вывод сокращается (`reduce_output`): ANSI снимается, длинные строки режутся с
  пометкой `… (+N симв.)`, повторы схлопываются в `[×N]`. Это искажение формы, а не
  содержания: точный вывод целого файла читай через `read`, не через `cat`.

`ctx` — управление рабочим контекстом: `action: commit` (применить правку
`LIVE_CONTEXT.json`), `status` (путь, бюджет, цель), `clear` (вырезать результаты
инструментов: `call_ids`, `before`, `keep_last`, маски `tool`/`min_bytes`).

Все остальные инструменты — программы в PATH
--------------------------------------------

Тулы реестра — отдельные бинари (agent, audit, desk, edit, fetch, grep, memory, read,
search, shot, view, web, write). Ядро находит их в каталоге тулов (`tools_dir`,
дефолт `~/.local/share/snens/tools`; при установке из исходников — `<репозиторий>/tools`),
зовёт `<тул> --help` при первом обращении и берёт описание для модели оттуда
(первая строка — суть, вторая — usage). Рядом с бинарником может лежать
`schema.json` — тогда у тула типизированный интерфейс: модель видит настоящие поля,
а argv/stdin собирает ядро (см. tools.txt и docs/tools-typed-schema.md). Нет
`schema.json` — контракт generic: `args` (массив или строка argv) + `stdin`.

Что ядро даёт любому вызову, независимо от схемы: `cwd` (рабочий каталог вызова,
разрешается от каталога сессии) и `timeout_seconds`. Каталог сессии меняется, когда
`run` выполнил `cd` — последующие read/edit/write/grep видят ту же точку отсчёта.

Переменные окружения, которые ядро передаёт тулам: `SNENS_SESSION`, `SNENS_CONFIG`,
`SNENS_SESSIONS_DIR`, `SNENS_CWD`, `SNENS_MAIL_DIR` (ящик подагентов),
`SNENS_PARENT` (у подагента), `SNENS_CONTEXT_PATH` (путь к `LIVE_CONTEXT.json`),
`SNENS_ATTACH_DIR` (канал вложений, если вложения включены), `SNENS_PRIV` (брокер
привилегий), `SNENS_APPROVAL_SOCK` (сокет одобрений), `SNENS_ASKPASS_DISABLED`.

Конвенции работы
----------------

1. Не читай файл целиком. Сперва `grep -n <символ>` (или `grep --files-only`),
   потом `read --offset N --limit M` по найденному месту. `read` без границ отдаёт
   400 строк и режет по `--max-chars` (дефолт 40 000).
2. Не выдумывай вывод команды — сначала выполни. Не додумывай содержимое файла —
   прочитай.
3. Точечная правка — `edit` (точный фрагмент), новый файл или полная перезапись —
   `write`. `sed -i` и `python3 - <<PY` для правки файлов — цена контракта, а не
   привычка: они обходят проверку «ровно одно совпадение» и ломаются молча.
4. `grep` тула — литеральный, без регулярок; `--word`, `--ignore-case`, `--glob`.
5. Долгий поиск по смыслу — `search` (SearXNG), чтение страницы — `fetch`
   (markdown, при 403/429 — fallback на r.jina.ai), скриншот — `shot`.
6. Инструмент мешает по ходу работы (вызов пришлось повторять, контракт путает,
   вывод пришлось дочитывать) — сразу тикет, не «потом».

Файлы инстанса
--------------

Каталог данных — `~/.local/share/snens` (XDG: `$XDG_DATA_HOME/snens`, переопределяется
`SNENS_DATA_DIR`). Конфиг — `~/.config/snens/config.toml` (`SNENS_CONFIG_DIR`,
`SNENS_CONFIG`), ключи API — `~/.config/snens/.env` (ядро читает их само; env процесса
сильнее файла).
| путь | что |
|---|---|
| `soul.md` | кто я, тон, рамки — первое лицо инстанса |
| `user.md` | кто человек: язык, город, привычки работы |
| `memory.md` | долгие факты, нужные в любой сессии (≤4 КБ: уезжает в префикс) |
| `skills/<имя>/SKILL.md` | скилл; в промпт едет только оглавление (name + description) |
| `skills/<имя>/references/*.md` | детали скилла, читаются по требованию |
| `skills/<имя>/scripts/*` | запускаемые проверки/хелперы скилла |
| `tickets/*.md` | тикеты: неудобства и возможности, markdown + front-matter |
| `sessions/<id>.jsonl` | журнал сессии; `<id>.out/` — дампы и `LIVE_CONTEXT.json` |
| `mail/<id>/` | ящик подагентов и steer (родитель ↔ ребёнок) |

`soul.md`, `user.md`, `memory.md` читаются каждый ход и приклеиваются к системному
промпту — поэтому они и живут отдельно от кода, их правит агент (memory.md) и человек
(user.md). Оглавление скиллов собирается из front-matter `SKILL.md`; тело скилла в
промпт не едет — скилл, о котором модель не знает, не существует, но и платить за
все тела каждый ход нельзя.

Каталоги по умолчанию
---------------------

- `sessions_dir` — `<data>/sessions`
- `tools_dir` — `<data>/tools`; из исходников — `<репозиторий>/tools`, рядом
  создаётся `<репозиторий>/bin` с симлинками на бинари тулов
- `skills_dir` — `<data>/skills`
- `tickets_dir` — `<data>/tickets`
- `mail_dir` — `<data>/mail`

Подкоманды ядра (что видно агенту): `snens tools [--json]` — список тулов и
определения для модели; `snens sessions`; `snens show|log [--session ID]`;
`snens tickets [--all|show|grep|stats]`; `snens model [slug]`; `snens config
[ключ=значение]`; `snens memory [on|off] [recall …] [retain …]`; `snens build
[<tool>…]`; `snens review`, `snens improve`, `snens selftest`, `snens verify`.
