plugins.txt — плагины и расширения snens
========================================

Принцип: ядро узкое, расширения — отдельные программы и файлы. Ядро не собирает
плагины внутрь: у него только контракты (argv + stdin для тулов, markdown-файлы для
скиллов и инстанса, конфиг TOML). Поэтому расширение ставится и удаляется без правки
ядра.

1. Долгая память (`tools/memory`, репозиторий snens-memory)
-----------------------------------------------------------

Плагин, а не сервис: один бинарь `memory`, один файл SQLite (FTS5 + sqlite-vec),
без демона и без Postgres. Публичный репозиторий —
https://git.svuvi.ch/svuvich/snens-memory; в дереве snens он подключён членом
workspace `tools/memory`, поэтому собирается той же командой, что и тулы
(`snens build`), и уезжает в установщик.

Контракт, который знает ядро (ничего другого оно не умеет):

  memory recall <текст>     # строки фактов; пусто = нечего сказать
  memory retain             # JSON {"user","assistant"} на stdin → очередь на дистилляцию
  memory flush              # очередь → факты (LLM извлекает 0–5 фактов + эмбеддинги)
  memory stats              # живые/устаревшие факты, очередь, типы
  memory reindex            # досчитать вектора, если провайдер лежал
  memory forget <uid>       # закрыть факт по uid (остаётся в таймлайне, но не выдаётся)
  memory import             # разовый импорт {"units":[{text,kind,subject}]}

Как читает: запрос → BM25 (FTS5, unicode61) ∪ вектор (sqlite-vec, int8) → RRF(k=20)
→ реранк (cross-encoder) → относительный порог → ≤N фактов. Пустая выдача — законный
исход: один нерелевантный факт роняет точность сильнее, чем помогает случайный.
LLM на пути чтения нет.

Как пишет: `retain` только кладёт ход в очередь (ноль сети, ядро зовёт его после
каждого ответа и ждать не должно), `flush` разбирает очередь отдельным запуском
(таймером или руками). Дедуп по векторам, перекрытие — через `supersedes`: старый
факт получает `valid_to` и остаётся в таймлайне.

Включено по умолчанию: секции `[memory]` нет → `enabled = true`,
`recall = "always"`, `retain = true`, `cmd = "memory"`. Нет бинаря в PATH — канала
просто нет, тихо, без ошибки хода. Тумблеры без правки файла:
`snens memory [on|off] [recall always|session|off] [retain on|off]`.

Режим `recall` — политика впрыска справки в системный префикс: `always` — каждый ход,
`session` — один раз на сессию, `off` — только по явному вызову тула. Справка короткая
(`max_facts = 6`, `max_tokens = 400`), потому что живёт в префиксе и платится каждый ход.

Свой конфиг — `~/.config/snens/memory.toml` (рядом с конфигом ядра):

```toml
db = "~/.local/share/snens/memory.db"
api_base = "https://api.example.com/v1"   # любой OpenAI-совместимый
embed_model = "<модель эмбеддингов провайдера>"
distill_model = "<дешёвая модель для извлечения фактов>"
rerank_model = "<реранкер>"               # rerank = "off" — выключить
max_facts = 6
max_tokens = 400
```

Ключ — `SNENS_API_KEY` (env или `~/.config/snens/.env`); реранкер может жить у
другого провайдера — тогда свой ключ в переменной, имя которой задаёт конфиг.

Чем это не является: не замена `memory.md`. `memory.md` — короткие факты, которые
нужны в любой сессии и уезжают в префикс всегда; плагин — большая библиотека, из
которой достаётся релевантное.

2. Скиллы (`skills_dir`)
------------------------

Скилл — каталог с `SKILL.md`, лежит в `skills_dir` (дефолт
`~/.local/share/snens/skills`; у инстанса из исходников может указывать в репозиторий,
потому что скилл описывает код и версионируется вместе с ним).
Формат `SKILL.md` — тот же, что у плагинов Claude/Anthropic: YAML front-matter и
markdown-тело.

```markdown
---
name: snens-harness
description: Как работать над snens — конвенции, команды, грабли
---

# тело скилла: оглавление, конвенции, питфоллы
```

Обязательны только `name` и `description`; `description` — то, по чему ядро (и
модель) решает, нужен ли скилл. Ядро собирает **оглавление**: по строке на скилл
вида `- <name>: <description>` из front-matter. Тело в системный промпт не едет —
скилл, о котором модель не знает, не существует, но платить за все тела каждый ход
нельзя. Прочитав оглавление, агент читает нужный `SKILL.md` по требованию.

Рядом со `SKILL.md` могут лежать:

- `references/*.md` — детали на один уровень глубже, читаются по требованию;
- `scripts/*` — запускаемые проверки и хелперы скилла.

Поставка приносит один встроенный скилл — `tickets` (разбор тикетов: сбор
частот, отбор «в ядро или в инстанс», закрытие с историей). Он раскладывается
на первом запуске в пустой `skills_dir`; существующий каталог не трогается
никогда. Посмотреть и поставить: `snens skills`, `snens skills install
[--force] [<имя>…]`. `--force` перезаписывает вашу версию — по умолчанию
локальные правки неприкосновенны.

Скилл — данные, а не код: чтобы добавить возможность, достаточно каталога с
`SKILL.md`. Оглавление собирается при каждой сборке промпта, поэтому новый скилл
виден со следующего хода, без перезапуска.

3. Тулы как самостоятельные программы
-------------------------------------

Тул — отдельный бинарь с контрактом «argv + stdin → stdout + код возврата». Ядро
знает о нём ровно три вещи: имя, путь к бинарю и (если есть) `schema.json` рядом.
Поэтому тул можно написать на любом языке и положить в `tools_dir` — ядро подхватит
его при следующем запуске, без правки `src/` и без пересборки ядра.

Соглашение о каталоге: `tools/<имя>/<имя>` (бинарь или симлинк), рядом
`tools/<имя>/schema.json` (необязателен), `selftest.sh` (необязателен). В дереве snens
все тулы — члены cargo-workspace, каждый задуман как самостоятельный репозиторий:
ядро не тащит их зависимости, а `snens build [<тул>…]` собирает их и кладёт бинари на
место.

Два обязательных требования к тулу:

1. `--help` — первая непустая строка: суть в одну строку; вторая: usage. По ним
   ядро строит описание инструмента для модели. Пустой `--help` = тул теряется
   (в stderr уйдёт «пустой --help»).
2. `schema.json` — если хочешь типизированный интерфейс: JSON Schema объекта плюс
   ключ `x-snens` с описанием, как поля становятся argv/stdin. Формат:
   `{"argv":[{"field":"path"},{"flag":"--offset","field":"offset"}],"stdin":{"mode":"none|field|json"}}`.
   Тогда модель видит настоящие поля, а argv собирает `serde_json`, а не модель на
   глаз (это снимает главный класс отказов `edit`: два уровня экранирования).
   Нет `schema.json` — контракт generic: `args` (array|string) + `stdin` (string).

Список тулов поставки: agent, audit, desk, edit, fetch, grep, memory, read, search,
shot, view, web, write — плюс вшитые `run` и `ctx`. Полные справки и поля — в
tools.txt; дизайн типизированной схемы и замеры — в `docs/tools-typed-schema.md`.

4. Что расширением не является
------------------------------

- Поверхности (TUI, веб-клиент, Telegram) — не плагины, а части продукта.
- Провайдер модели — не плагин: это конфиг (`[providers.<имя>]`, `base_url`,
  `key_env`, `body_patch`, `headers`), нового кода не требует.
- Инстанс (soul/user/memory, тикеты) — данные, а не расширение; они не публикуются
  вместе с кодом.
