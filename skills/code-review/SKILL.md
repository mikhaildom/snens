# Ревью кода: охват каждого файла, а не впечатление от диффа

Когда просят «сделай ревью», «проверь правки», «посмотри ветку перед мержем».
Ревьюер — ты сам (модель этой сессии). Если на машине есть
[open-code-review](https://github.com/alibaba/open-code-review) (`ocr`), он
выбирает файлы и правила проверки; если нет — то же делается обычным git.

Все команды — через `run`. Git — всегда `git --no-pager`, дифф — без внешних
программ и цвета: `--no-ext-diff --no-textconv --no-color`.

## 1. Что смотреть

Определи режим по просьбе:

| просьба | режим | ключи |
|---|---|---|
| «мои правки», ничего не сказано | рабочая копия | — |
| «ветка X против main» | диапазон | `--from main --to X` |
| «текущая ветка против main» | диапазон | `--from main` (до `HEAD`) |
| «коммит abc123» | коммит | `-c abc123` |

**Есть `ocr`** (`ocr --version` отвечает):

```
ocr delegate preview --format json [--from <ref> [--to <ref>]] [-c <hash>]
```

Даёт `mode`, `merge_base`, список `reviewable_files` (путь, статус, строки) и
`excluded_files` с причиной. Правила проверки по файлам:

```
ocr delegate rule --format json [те же ключи] <путь1> <путь2> …
```

Правила сгруппированы: у файлов с одинаковым правилом — одна группа. Если
`--format` не понят («unknown flag») — повтори без него и читай текстовый вывод.

**Нет `ocr`** — список файлов сам:

```
git --no-pager diff --name-status <merge_base>..<to>      # диапазон; merge_base = git merge-base <from> <to>
git --no-pager show --name-status --format= <hash>        # коммит
git --no-pager status --porcelain                         # рабочая копия (+ неотслеживаемые)
```

Исключи сгенерированное и чужое: lock-файлы, `dist/`, `target/`, вендоренные
крейты/пакеты, бинарники, картинки. Каждое исключение запиши с причиной.

## 2. Дифф каждого файла

- диапазон: `git --no-pager diff --no-ext-diff --no-textconv --no-color <merge_base>..<to> -- "<путь>"`
- коммит: `git --no-pager show --no-ext-diff --no-textconv --no-color <hash> -- "<путь>"`
- рабочая копия: `git --no-pager diff --no-ext-diff --no-textconv --no-color HEAD -- "<путь>"`;
  новый неотслеживаемый файл читай целиком (`read`) — весь он новый код.

Большой дифф — в файл (`--output=<абсолютный путь вне репозитория>`), читай
кусками через `read`, потом удали. Контекст вокруг правки — `read` по номерам
строк, `git --no-pager log --oneline -- "<путь>"`, `git --no-pager blame`.

## 3. Проверка

Заведи список всех файлов из шага 1. По каждому:

1. дифф и, где нужно, окружающий код;
2. правило из `ocr delegate rule` (если есть) — как чек-лист;
3. ищи: ошибки логики и граничные случаи, гонки, утечки ресурсов,
   безопасность (ввод снаружи, пути, команды, секреты в коде), потерю данных,
   обработку ошибок, производительность на горячем пути, отсутствие тестов на
   новое поведение, расхождение с соседним кодом;
4. отметь файл `проверен` или `пропущен: <конкретная причина>`.

Большие правки — пачками по общим правилам и размеру. Не останавливайся на
первой серьёзной находке: охват важнее.

Каждую находку проверь, прежде чем записать: открой код, убедись, что сценарий
реален. Сомнительное — выкинь молча, а не «на всякий случай».

## 4. Отчёт

Сначала охват: `всего файлов N, проверено M, пропущено K (причины), охват M/N`.
Каждый файл из шага 1 должен быть в одной из групп — молча выпавших не бывает.

Потом находки по тяжести:

- **критично / высоко** — баги, безопасность, потеря данных: всегда;
- **средне** — производительность, обработка ошибок, сопровождаемость: с контекстом;
- **низко** — стиль, мелочи: только если правда полезно.

Находка: `путь:строка[-строка]`, что не так, при каких входных данных ломается
(конкретно), категория (bug, security, performance, maintainability, test,
style, documentation).

## 5. Исправление (только если просили «ревью и почини»)

Критичное и высокое — правь сразу и прогони тесты. Среднее — опиши, что
менять. Низкое — пропусти, если правка не тривиальна. В отчёте у каждой
находки: исправлено / оставлено / не нужно.
