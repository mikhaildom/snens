# Тикеты: как разбирать, а не пересказывать

Тикет — это запись о том, что повторялось и мешало. Работа с ним: найти частые,
отделить баг продукта от особенности инстанса, починить, закрыть так, чтобы
следующий разбор не начинался с нуля.

## 1. Где что лежит

- Каталог — `cfg.tickets_path()` (дефолт `<данные>/tickets`), по файлу на тикет.
- Имя файла: `YYYY-MM-DD-короткое-имя.md`. Подкаталогов нет.
- Просмотр — командой, не `read`:
  ```
  snens tickets                 # открытые, сортировка по hits
  snens tickets --weight        # сортировка по заявленной тяжести
  snens tickets --all --target run --family long-running-jobs
  snens tickets show <префикс>  # тело тикета (префикс имени достаточно)
  snens tickets grep <текст>    # поиск по телу, отсортировано по hits
  snens tickets stats           # сколько открыто, разбивка по target
  ```
  `tickets grep` ищет и в закрытых, если добавить `--all` — это дешевле, чем
  перебирать файлы руками.

## 2. Фронтматтер: что реально читает ядро

```markdown
---
status: open          # open | done | closed — по нему фильтрует listing
kind: defect          # defect | opportunity | tool
target: run           # ядро | тул | harness | instance — куда чинить
family: long-running-jobs   # одна беда под разными именами
weight: 4             # заявленная тяжесть, 1..5
hits: 8               # сколько раз симптом возвращался
---
```

`hits` — **не** автоматический счётчик: его поддерживает тот, кто разбирает.
Растёт он по свидетельствам из логов (см. ниже), а не по «кажется, часто».

## 3. Сбор частот: топ-N без выдумок

Два независимых источника, и они отвечают на разные вопросы.

**а) Заявленные `hits` — что уже заметили.**

```sh
snens tickets --all | sort -t'|' -k4 -r    # грубо: глазами по колонке hits
snens tickets stats                         # где вообще болит
```

**б) Реальные вызовы в логах — что подтверждается.** Логи сессий —
`sessions/<id>.jsonl`, по записи на событие (`{"kind": "tool_result", ...}`).
Считать надо по отказу, а не по вызову: тикет открывают на `exit != 0`.

```sh
# сколько раз конкретный отказ встретился во всех логах
grep -l "" sessions/*.jsonl >/dev/null 2>&1
python3 - <<'PY'
import json, glob, collections
c = collections.Counter()
for p in glob.glob('sessions/*.jsonl'):
    for line in open(p, encoding='utf-8', errors='replace'):
        try: r = json.loads(line)
        except Exception: continue
        if r.get('kind') != 'tool_result': continue
        if r.get('exit', 0) == 0: continue
        body = r.get('body') or {}
        text = body.get('text', '') if isinstance(body, dict) else str(body)
        # ключ — первая строка отказа без путей и чисел: так похожие отказы сливаются
        first = text.strip().split('\n')[0][:80]
        if first: c[first] += 1
for k, v in c.most_common(30): print(v, '|', k)
PY
```

Правила, без которых счёт врёт:
- **Считать семьи, а не файлы.** Один баг под тремя именами (`…-timeout`,
  `…-engines-timeout`, `…-pool-wedge`) — это один тикет и один вес.
- **Отделять «до фикса» от «после».** `hits` накапливались до починки; после
  неё счётчик не пересчитывается автоматически. Если при разборе выяснилось,
  что тикет закрыт по существу — это пишется в `## История`, а не молча.
- **Отказы-следствия не считать.** `exit=127 command not found` от фонового
  задания — это один баг, а не десять «нет тула».

## 4. Главный критерий: ядро или инстанс

Вопрос ровно один: **повторится ли это на другой машине с этой моделью?**

| Признак | Куда | Пример |
|---|---|---|
| Воспроизводится на чистой установке, дело в контракте тула/ядра | `target: harness` / имя тула | отказ валидатора стирает черновик; `agent result` для живого ребёнка отдаёт exit=1 |
| Зависит от конфига, железа, сети, чужих сервисов этой машины | `target: instance` | все движки SearXNG в timeout; диск забит |
| Требует решения человека: версия, релиз, удаление данных, sudo | не чинится молча — вопрос | бамп версии, рестарт прода |
| Одноразовая особенность площадки | закрывается как `done` с причиной | «на этом хосте не ставится webkit» |

Инстанс-фиксы **не меняют продукт**: правится конфиг, юнит, `.gitignore`
инстанса, ставится таймер. Если для инстанс-проблемы понадобилась правка
`src/` — значит критерий определён неверно, вернись к таблице.

## 5. Разбор: от симптома к причине

1. Прочитай `## Симптом`, `## Воспроизведение`, `## Гипотеза`. Если
   воспроизведения нет — оно пишется первым делом: без него чинится догадка.
2. Найди подтверждение **в коде или в живом запуске**, а не по названию
   тикета: `grep` по символу в репозитории, затем честная проверка командой.
3. Отличай «выглядит как» от «измерено». «Все движки timeout» — не «лимиты
   апстримов» (у лимитов другие причины: 429/403/suspended), а сеть процесса.
   Проверка, которая это различает, стоит одной команды.
4. Чини причину, а не сообщение. Если причина в другом месте — открой новый
   тикет со ссылкой, а этот закрой с указателем.

## 6. Закрытие: что писать, чтобы следующий раз был дешевле

Дописать в конец тела, не переписывая исходное:

```markdown
## История
- 2026-11-19 сессия <id>, вызовы [n–m] — что проверено и чем закончилось.
- 2026-11-19 РЕШЕНО: причина в X (файл:строка), проверка: `<команда>` → вывод.
  Правка: <коммит>. Рецидив возможен, потому что …; мера — <таймер/проверка>.
```

Закрытие:
- `status: done` — причина найдена и устранена либо признана не-багом.
- `status: closed` — решено не делать.
- `hits` не обнулять: это история наблюдений.

Правила:
- Закрывая, **всегда** назови проверку, которой убедился. «Должно работать» —
  не проверка.
- Если фикс потребовал новой меры (таймер, cron, ручной шаг) — это в тикете
  одной строкой, иначе мера забудется и симптом вернётся.
- Если тикет закрыт частично — оставь `status: open` и напиши, что осталось.
- Старый тикет, чья причина найдена при разборе другого, **закрывается** со
  ссылкой на новый. Дубли, оставленные открытыми, съедают следующий разбор.

## 7. Заведение нового тикета

Пиши сразу после неудобства, пока факт жив: через ход детали забываются.
Минимум — то, без чего тикет бесполезен:

```markdown
---
status: open
kind: defect
target: <ядро|тул|harness|instance>
weight: 2
hits: 1
---
## Симптом / что повторяется
Что случилось, одной фразой, с точным сообщением об ошибке.
## Воспроизведение
Команда и что она вернула. Сессия и номера вызовов, если известно.
## Гипотеза / предложение
Где, по-твоему, причина и что менять. Явно помечай догадку как догадку.
```

## 8. Границы

- Не чинить в тикете то, что требует решения человека: версия и релиз,
  удаление данных, sudo, рестарт прода в ходе разговора.
- Не «оптимизировать» тикет, который не воспроизводится: сначала
  воспроизведение, потом правка.
- Не пересказывать историю ради пересказа: в `## История` — только то, что
  проверено, иначе следующий разбор пойдёт по ложному следу.
