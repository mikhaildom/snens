# Десктоп-приложение snens

Оболочка Tauri 2: окно с веб-клиентом и ядро `snens` как дочерний процесс.
Один установщик, одно обновление — ядро, тулы и клиент едут внутри бандла.

## Раскладка после установки (Windows, per-user, без UAC)

```
%LOCALAPPDATA%\snens\
├── snens-desktop.exe      # окно (Tauri)
├── snens.exe              # ядро: HTTP/API + статика клиента (sidecar)
├── memory.exe             # плагин долгой памяти (sidecar)
├── tools\                 # тулы: read, edit, run-инструменты, shot, web, desk…
│   ├── read\read.exe
│   └── …
└── web\                   # собранный клиент (dist из snens-web)
    ├── index.html
    └── assets\…
```

Данные и конфиг — как у обычного snens (`%APPDATA%\snens`): установка их не
касается, удаление их не трогает.

### Где искать тул в PATH: `bin/` — в каталоге данных, а не установки

Ядро раскладывает ссылки на тулы в `bin/`, чтобы они были видны из `run`. В
поставке этот каталог живёт в `%APPDATA%\snens\bin`, **а не** в
`%LOCALAPPDATA%\snens\bin`: установленный бандл только для чтения и
перезаписывается обновлением, а `bin/` — производная раскладка. На Windows
вместо симлинков (они требуют прав) там жёсткие ссылки на те же exe, поэтому
второго комплекта файлов на диске нет; на unix — симлинки.

Историю вопроса стоит знать: до этого `bin/` лежал рядом с `tools/` в каталоге
установки, и на Windows каждая копия тула была полноценной копией файла — рядом
с `tools\fetch\fetch.exe` появлялся `bin\fetch.exe`, ещё 4.5 МБ. Выглядело как
«установщик положил всё дважды».

## Почему так

- **Ядро — sidecar, а не сервис.** На Windows служба требует администратора и
  живёт в сессии 0, где нет ни профиля пользователя, ни UI. Поэтому ядро —
  обычный дочерний процесс окна, с `CREATE_NO_WINDOW`: консольного окна нет, а
  жизнь процесса привязана к окну.
- **Консоли у GUI нет вообще.** У самого `snens-desktop.exe` стоит атрибут
  `windows_subsystem = "windows"`, а у дочернего ядра — `CREATE_NO_WINDOW`.
  Раньше не было ни того, ни другого: рядом с интерфейсом открывалось пустое
  чёрное окно терминала, и его закрытие убивало приложение.
- **Обновление одно на всё.** Sidecar'ы — часть бандла, поэтому
  `tauri-plugin-updater` тянет новый `-setup.exe`, а тот перезаписывает и
  `snens.exe`, и тулы, и `web\`. Никакой сборки на машине человека: cargo, node
  и rustc в поставке не нужны.
- **Один процесс отдаёт и API, и клиент.** `snens serve` умеет `ServeDir` на
  `web\` (см. `SNENS_WEB_DIR` в ядре), поэтому отдельный vite/npx в поставке не
  участвует — это была бы dev-зависимость в продукте.
- **Окно всегда грузит свой клиент.** Даже при подключении к чужому ядру
  (`WebviewUrl::App`, не `External`): иначе интерфейс ехал бы с сервера, а экран
  подключения — часть нашего бандла — стал бы недоступен. Ядро при этом живёт на
  другом хосте, CORS у него открыт.

## Трей и закрытие окна

Иконка в системном трее (`src/tray.rs`) с меню: «Открыть окно», «Перезагрузить
интерфейс», «Выход (остановит ядро)». Крестик окна **прячет** окно, а не
завершает приложение: ядро держит долгие ходы и подагентов, и случайный клик по
крестику не должен их убивать. Выход — явный пункт меню (и он гасит ядро, чтобы
следующая установка могла перезаписать файлы).

Иконка — знак из приветственного экрана (жирная `s` на чёрном поле), исходник —
`icons/icon-source.html`, пересборка — `scripts/make-icons.sh` (рендерит размеры
headless-хромом и склеивает `.ico` скриптом `scripts/make-ico.py`; ImageMagick и
Pillow на машине релиза не требуются).

## Пейринг: ядро на другом устройстве

Оболочка работает в двух режимах, и переключаются они из настроек клиента
(раздел «соединение»), а не флагами запуска:

1. **Локальное ядро** (по умолчанию): оболочка поднимает sidecar на свободном
   порту и открывает окно на нём.
2. **Удалённое ядро**: окно показывает форму подключения (адрес + код из
   `snens pair` на сервере). Оболочка сохраняет адрес и токен в файле
   `%APPDATA%\ch.svuvi.snens\connection.json` и при следующем запуске **своего
   ядра не поднимает**. «Вернуться к своему ядру» в настройках стирает этот файл.

Токен в web-view попадает через `window.__SNENS__ = {baseUrl, token, shell,
remote}`, который оболочка выставляет при **создании** окна. Поэтому после смены
соединения оболочка пересоздаёт окно (команда IPC `reopen`): `location.reload()`
оставил бы клиент на старом адресе — проверено.

В браузере (не в окне) пейринг по-прежнему кладёт соединение в `localStorage`;
ветку выбирает `src/lib/shell.ts`.

## Сборка

```sh
# 1. Клиент
cd ../snens-web && npm ci && npm run build      # → dist/

# 2. Бинари ядра и тулов, с суффиксом target-triple (требование Tauri sidecar)
cd ../snens && cargo build --release --workspace
scripts/desktop-stage.sh                        # раскладывает binaries/ и resources/

# 3. Приложение
cd desktop && npm ci && npx tauri build
```

`scripts/desktop-stage.sh` — единственное место, где записано соответствие
«что куда кладётся»: бинарники получают суффикс `-<target-triple>`, клиент
копируется в `resources/web`.

Релиз целиком (сборка + `latest.json` для апдейтера) — `scripts/release.sh`;
он же печатает команду выкладки на `releases.svuvi.ch`.

## Что осталось проверить на живой Windows

- Регистрация автозапуска (плагин `autostart`, HKCU Run) — права обычного
  пользователя.
- Поведение NSIS при обновлении, когда ядро держит файлы: его надо гасить до
  запуска инсталлятора, иначе Restart Manager его не увидит (он знает только
  главный exe).
