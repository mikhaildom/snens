# Релиз

Как выпускать snens так, чтобы ничего не забывалось. Три вещи решают всё:
**одна версия**, **гейт перед сборкой**, **проверка на выложенном артефакте**.

## Почему это здесь записано

Версия 0.2.4 была собрана с правок, проверенных только на двух машинах автора:
смоук не запускался, тестов клиента в гейте не было вовсе, тег не ставился.
Ошибки находились уже у людей. Процесс ниже — плата за то, чтобы это не
повторялось.

## Что считается релизом

| канал | артефакт | где собирается |
|---|---|---|
| десктоп | `snens_<версия>_x64-setup.exe` (Windows), AppImage/deb | Windows-машина (`ssh svuv`), на сервере нельзя — нет glib/webkit |
| веб-клиент | `snens-web_<версия>_linux-x86_64.tar.gz` | сервер, `scripts/web-release.sh` |
| ядро (сервис) | immutable-релиз по sha в `~/.local/lib/snens/releases/` | сервер, `scripts/prod-restart.sh` |
| Telegram | отдельный репозиторий, свой релиз | где угодно, `go build` |

Версия одна на всё: `Cargo.toml` (ядро) = `web/Cargo.toml` = `desktop/Cargo.toml` =
`desktop/tauri.conf.json` = `desktop/package.json`. Источник правды — корневой
`Cargo.toml`, остальные файлы производные.

## Порядок

### 1. Поднять версию

```sh
scripts/version.sh --set 0.3.0     # правит все пять файлов
scripts/version.sh --check         # расхождение — код 1
```

Версия не поднимается «на всякий случай»: пока правки не проверены, версия
остаётся прежней.

### 2. Проверить на стенде

Стенд — отдельный инстанс, не второй бинарник:

```sh
systemctl --user restart snens-dev snens-dev-web     # :7440 и :5175
```

Что проверяется руками (то, что не покрыто тестами): ход в веб-клиенте, стрим,
отправка во время идущего хода (steer), подагент и его карточка после
завершения, переподключение после рестарта ядра.

### 3. Прогнать гейт

```sh
scripts/release-check.sh           # 5–15 минут, полный
scripts/release-check.sh --fast    # без cargo test и смоука
```

Гейт проверяет и **падает**, если:

1. версии в пяти файлах расходятся;
2. worktree грязный (релиз из незакоммиченных правок не воспроизводим);
3. нет тега `v<версия>` или он не на HEAD;
4. `cargo test --workspace` не зелёный;
5. `scripts/production-smoke.py` не зелёный (13 проверок поверхности и TUI);
6. тесты или сборка веб-клиента не зелёные;
7. контент сайта не сходится (`scripts/site.py --check`);
8. `snens selftest` не прошёл.

### 4. Закоммитить и поставить тег

```sh
git commit -am "release: 0.3.0"
git tag -a v0.3.0 -m "0.3.0"
scripts/release-check.sh           # теперь все восемь пунктов зелёные
```

### 5. Собрать артефакты

```sh
# десктоп — на Windows-машине, с ключом подписи (он только там)
TAURI_SIGNING_PRIVATE_KEY_PATH=~/.config/snens/updater.key scripts/release.sh

# веб-клиент — на сервере
scripts/web-release.sh
```

Оба скрипта начинают с гейта: собрать артефакт с непроверенного дерева нельзя
без `--skip-gate`, и это флаг только для отладки самого скрипта.

### 6. Выложить и проверить **выложенное**

```sh
SNENS_RELEASE_PUBLISH=1 TAURI_SIGNING_PRIVATE_KEY_PATH=… scripts/release.sh   # десктоп
scripts/web-release.sh                                                        # веб (выкладывает сам)
scripts/site-publish.sh                                                       # сайт
```

Проверка не «файл лежит», а «файл работает»:

```sh
curl -sI https://snens.svuvi.ch/releases/latest.json | head -1          # 200
curl -s  https://snens.svuvi.ch/releases/latest.json | head -20          # версия та
curl -sI https://snens.svuvi.ch/releases/web/0.3.0/snens-web_0.3.0_linux-x86_64.tar.gz | head -1
cd /tmp && curl -sO <url> && tar xzf <архив> && ./snens-web --help     # запускается
```

Установщик Windows проверяется запуском на чистой машине: установка, первый
запуск, окно грузит свой клиент.

### 6а. Выкладка десктоп-артефакта, собранного на Windows

`scripts/release.sh` собирает бандл на сервере и выкладывает сам, но
Windows-установщик собирается на другой машине (`ssh svuv`). Его выкладка —
четыре шага, и все они обязательны:

```sh
# 1. забрать артефакт и подпись с машины сборки
scp svuv:'.../bundle/nsis/snens_<версия>_x64-setup.exe{,.sig}' /tmp/rel/

# 2. latest.json: version + url + signature из .sig (байт в байт, без trim)
#    platforms: только то, что реально подписано — "windows-x86_64-nsis"

# 3. каталог версии и владелец. `sudo mkdir` создаёт root-каталог, и после
#    этого `cp` падает Permission denied: сначала создать, потом chown.
sudo mkdir -p /var/www/snens.svuvi.ch/releases/<версия>
sudo chown -R clawdich:clawdich /var/www/snens.svuvi.ch/releases/<версия>
cp -p /tmp/rel/* /var/www/snens.svuvi.ch/releases/<версия>/
chmod 0755 /var/www/snens.svuvi.ch/releases/<версия>
chmod 0644 /var/www/snens.svuvi.ch/releases/<версия>/*

# 4. манифест — АТОМАРНО и последним: пока его нет, старый latest.json
#    обещает старую версию, и никто не скачает 404.
cp /tmp/rel/latest.json /var/www/snens.svuvi.ch/releases/.latest.json.tmp
mv -f /var/www/snens.svuvi.ch/releases/.latest.json.tmp \
      /var/www/snens.svuvi.ch/releases/latest.json
```

Проверка — на скачанном файле, а не на «лежит»:

```sh
curl -s https://snens.svuvi.ch/releases/latest.json | python3 -m json.tool
curl -s -o /tmp/x.exe -w '%{http_code} %{size_download}\n' <url из манифеста>
sha256sum /tmp/x.exe      # совпадает с собранным на машине сборки
```

Установщик ставится в отдельный каталог (`/S /D=...`), чтобы не тронуть
рабочую установку. **Проверка установкой перезаписывает запись в реестре**
`HKCU\...\Uninstall\snens` на новый путь: после проверки её надо вернуть на
рабочий каталог (DisplayVersion, InstallLocation, UninstallString, DisplayIcon),
иначе «Удалить программу» ведёт в удалённую папку. Данные (`%APPDATA%\snens`)
установщик не трогает; чистый инстанс делается через `SNENS_DATA_DIR` и
`SNENS_CONFIG_DIR`, а не удалением чужого каталога.

### 7. Обновить рабочий сервис

```sh
scripts/prod-restart.sh --no-restart    # поставить релиз ядра, launcher переключить
systemctl --user restart snens           # отдельным шагом, не посреди разговора
```

Рестарт ядра рубит активную сессию (`done=error`). Веб-клиент переключается на
новый бинарь так же: положить `snens-web` и `web/` на место, перезапустить
`snens-web`.

## Откат

- ядро: `ln -sfn ~/.local/lib/snens/releases/<старый sha>/snens ~/.local/bin/snens`
  и рестарт. Каталоги релизов не перезаписываются.
- веб-клиент: распаковать прошлый архив поверх.
- десктоп: поставить прошлый `-setup.exe`; манифест `latest.json` при этом
  указывает на новую версию, поэтому откат — ручной.

## Что делать, если гейт упал

Не «перезапустить и посмотреть». Каждый пункт отвечает на свой вопрос:

| провал | что значит |
|---|---|
| версия | правили не тем скриптом или забыли `--set` |
| worktree | есть правки, которых нет в теге: коммить или спрятать |
| тег | релиз не помечен; `git tag -a v<версия>` |
| cargo test | код сломан — чинить, а не релизить |
| смоук | поверхность/TUI сломаны; смотреть `--verbose` вывод смоука |
| клиент | сломаны тесты или сборка бандла |
| сайт | ссылки/плейсхолдеры/манифест: `python3 scripts/site.py --check` |
| selftest | реестр тулов или контракт `--help` разъехались с кодом |

## Заметки, которые стоили времени

- **Caddy читает не нашим пользователем.** После выкладки `chmod 0755` на
  каталоги и `0644` на файлы: с `umask 077` сайт отдаёт 403, и это не видно ни
  в логе сборки, ни в `ls`. Оба скрипта делают это сами.
- **Сборка релиза — только на Windows.** `tauri build` требует glib/webkit,
  которых на сервере нет.
- **`latest.json` — единственный источник для кнопки установщика на сайте.**
  Сайт берёт адрес оттуда при сборке; без манифеста кнопка ведёт на страницу
  установки.
- **Имя каталога версии неизменяемо.** Люди со старой версией могут ещё качать
  её артефакт; перезапись ломает им обновление.
