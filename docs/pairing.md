# Пейринг: приложение на одном устройстве, ядро на другом

Задача: GUI (телефон, ноутбук, десктоп) ставится как обычное приложение, а ядро
snens живёт на другой машине — сервере, домашнем хосте, VPS. Человек должен
подключить одно к другому **без терминала и без копирования длинных строк**.

## Что уже есть и чего не хватает

Сейчас `snens serve` **требует loopback** (`surface_server::serve`,
`production::serve`): подключиться с другого устройства нельзя вообще. Это не
недосмотр — единственная защита API это bearer-токен в файле, и выставлять такой
порт наружу «как есть» небезопасно:

- токен один и навсегда, утечка = полный контроль (у ядра нет модели прав:
  пользователь и так даёт агенту полный доступ — см. ниже);
- TLS нет, а значит токен и содержимое разговоров шли бы открытым текстом;
- CORS не настроен: браузер с чужого origin просто не достучится.

Поэтому пейринг — это не «открыть порт», а три вещи: транспорт, обмен секретом,
и явная граница доверия.

## Модель доверия (осознанное решение)

Проект исходит из того, что владелец даёт агенту полный контроль над машиной,
где тот работает. Харнесс не строит внутри себя песочницу: ограничивать надо
**машиной/контейнером**, а не флагами. Из этого следует:

- никаких «гранулярных прав» для парного клиента: подключился — значит управляешь;
- защита нужна только от **чужого**, кто не прошёл пейринг. Поэтому вся
  безопасность — в транспорте (шифрование) и в одноразовости кода пейринга.

## Транспорт: два пути, один контракт

| путь | когда | что настраивать |
|---|---|---|
| **Хвост сети** (Tailscale/WireGuard/SSH-туннель) | основной | ничего в snens: адрес уже приватный и шифрованный |
| **Прямой TLS с самоподписанным сертификатом** | если хвоста нет | ядро отдаёт HTTPS, клиент запоминает отпечаток |

Первый путь предпочтителен и его надо поддержать первым: он не требует ни
сертификатов, ни доверия к самоподписи, а «приватная сеть» — уже привычная
вещь. Практически это значит: `serve --listen` должен принимать **любой**
адрес, но не молча, а с явным флагом `--allow-remote`, который печатает
предупреждение и (если TLS не настроен) требует, чтобы адрес был в приватной
сети (10/8, 172.16/12, 192.168/16, 100.64/10, fd00::/8).

Второй путь — `--tls-cert`/`--tls-key` (rustls уже в зависимостях через reqwest)
плюс вывод отпечатка SHA-256 для сверки.

## Обмен секретом: код пейринга

Проблема: токен длинный, вводить его руками на телефоне — издевательство.
Решение, знакомое по телевизорам и мессенджерам:

1. На ядре: `snens pair` (или кнопка в настройках веб-клиента на самом ядре)
   печатает **короткий код**: 6 цифр + срок жизни 5 минут. Код — не токен, а
   приглашение: он живёт в памяти процесса и одноразовый.
2. На клиенте: поле «код» в первом экране. Клиент шлёт
   `POST /v1/pair/claim {code, client_name, client_pubkey}`.
3. Ядро проверяет код, возвращает **постоянный токен** этому клиенту
   (и запоминает его в `~/.local/share/snens/clients/<id>.json`: имя, дата,
   отпечаток). В UI ядра — список подключённых устройств с кнопкой «отозвать».
4. Токен хранится на клиенте в защищённом хранилище ОС (Keychain/DPAPI/
   libsecret), не в localStorage.

Почему не просто «показать QR с токеном»: QR удобен, но токен в нём — тот же
постоянный секрет, и он попадает в историю камеры/скриншоты. QR с **кодом
пейринга** безопаснее и даёт ту же скорость: сканирование кода = один шаг.

Обмен по сети (когда ядро уже слушает) — единственный вариант для телефона;
`claim` ограничивается: код одноразовый, попытки считаются (5 и блокировка на
минуту), после успеха код умирает.

## Что видит человек (сценарий)

**Ядро на сервере:**
```
$ snens pair
Код пейринга: 481-902   (действует 5 минут)
Адрес: http://100.73.69.107:7420
Сканируйте QR в приложении или введите адрес и код.
```

**Приложение на телефоне:** первый экран вместо «введите токен» спрашивает
только адрес (или QR). Дальше — код. Всё. Токен человек не видит никогда.

Повторный запуск: приложение помнит адрес и токен, показывает статус
(`snens · сервер`, `snens · сервер недоступен`).

## Что нужно поменять в коде

| где | что |
|---|---|
| `src/production.rs`, `src/surface_server.rs` | `--allow-remote`: снять loopback-гейт, но с проверкой приватного адреса и предупреждением; `--tls-cert/--tls-key` |
| `src/surface_server.rs` | маршруты `POST /v1/pair/start` (только с локального адреса или из TUI), `POST /v1/pair/claim`, `GET/DELETE /v1/clients`; CORS для веб-клиента |
| `src/clients.rs` (новый) | реестр клиентов: id, имя, хеш токена, дата; проверка токена по реестру, а не по одному файлу |
| `src/cli.rs` | команда `snens pair` (+ `snens clients list/revoke`) |
| веб-клиент | экран «подключение»: адрес + код, хранение токена вне localStorage |
| десктоп-оболочка (Tauri) | тот же экран; токен в защищённом хранилище ОС |

## Открытые вопросы (решать при реализации)

- Хранить токены клиентов хешами (SHA-256) — да, чтобы файл реестра не был
  набором действующих секретов.
- Что делать с `SNENS_ASKPASS_DISABLED` в headless: привилегированные действия
  идут через канал одобрений в UI — при парном клиенте кнопка одобрения
  появляется у него, это уже работает.
- Обратная совместимость: локальные сценарии (TUI, веб на том же хосте)
  продолжают работать с одним токеном из `api.token`; реестр клиентов —
  дополнение, а не замена.
