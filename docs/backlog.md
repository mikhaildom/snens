# Бэклог

## Что осталось

Порядок — по ценности для главной цели: сопоставимый с чужим харнессом результат при
похожей цене, без привязки к чужому коду.

1. **Замер против эталона (Hermes).** N≥5 роллаутов одинаковых задач, парно; метрика —
   результат + tokens/task и деньги. Без этого всё остальное — догадки.
2. ~~Возобновляемость длинного прогона.~~ Лимит поднят до `max_turns`=200 и больше не
   крашит: при исчерпании цикл просит промежуточный итог и выходит с `Ok`. Осталось
   (по желанию): возобновляемость — продолжать незавершённый прогон по грязному дереву.
3. **Исход прерванного прогона.** Обрыв стрима провайдера сейчас просто валит запуск;
   автономному циклу нужно отличать «прогон не состоялся» от «прогон сломал репозиторий».
4. **Bootstrap: ядро правится через PR.** Публикация кода инстанса — без путей и сессий.
5. **Подагенты и steer.** Сделано: подагент — сессия отдельным процессом (`run --detach`),
   файловый ящик сессии (`mail/`), впрыск `Rec::Steer` на границе хода (steer человека и
   канал родитель↔ребёнок — один механизм), тул `agent` (start/wait/result/ask/send/list/
   kill), терминатор `Rec::Done` пишет харнесс (конец ребёнка не зависит от того, позвал ли
   он инструмент), supervisor держит родителя живым ради детей. Проверено живьём:
   родитель запустил подагента, дождался `Done`, получил итог.
6. **Демон + сокет (M5).** Все интерфейсы сводятся к двум операциям: дописать строку в лог
   и читать события; `source` в сообщении различает поверхность. На Windows unix-сокет →
   named pipe. **Не раньше второй поверхности:** у сокета с одним клиентом протокол будет
   угадан, а не выведен из практики. Точка инъекции уже проверена steer'ом без сокета;
   дальше — сам демон, к которому подключаются Telegram/Discord/приложение.
   Steer из TUI сделан: поле ввода живо во время хода (readline в отдельном потоке +
   ExternalPrinter), введённое уезжает в ящик сессии и впрыскивается на границе хода.
   Дизайн и отклонённые альтернативы — `docs/subagents.md`.
   Осталось у подагентов: роение (дерево/граф детей — сейчас одноуровневое), бюджет/квота
   на число детей.
7. **TUI (M6).** Сделано: `snens tui` — строка-редактор (история ввода, Ctrl+C отменяет ход,
   Ctrl+D выход), живой поток вывода тулов и расход по ходу, автопрогон ревью на выходе
   (фоновым процессом). Рендер одним слоем: рассуждение серым курсивом (`/reasoning`
   скрывает), вызовы третьим стилем, красная строка при ошибке, markdown-таблицы рамкой.
   Осталось: steer (ввод во время работы агента), мессенджеры как клиенты будущего сокета.
8. **Память и поиск** — внешний инструмент (Jev-классификатор), в ядре ни recall-механики,
   ни индексации.
9. **Тулы в свои репозитории** — когда на конкретный тул пойдут тикеты из ревью.
10. **Поиск по релевантности** — тикетов и оглавления скиллов: когда список открытых
    начнёт раздувать промпт (см. `docs/review.md`, раздел «Отложено»). Механизм общий.
11. **`audit`: `never-referenced` и `unused-tool`** — первому нужен проход по всем сессиям,
    второму — след за тем, всплыл ли результат дальше в диалоге.

## Диагностика после правок (LSP/линтеры)

Место — **не в `edit`/`write`**, а в цикле харнесса: после любого хода, оставившего
грязные файлы (`git status --porcelain`), гонять чекер по расширению изменённых файлов
и приклеивать диагностику к наблюдению. Тогда это работает и для `run sed -i`, а не
только для тулов правки.

- Соответствие «расширение → команда» берётся из `snens.toml` в корне проекта,
  найденного подъёмом вверх от изменённого файла.
- Чекеры — CLI (`cargo check --message-format short`, `tsc --noEmit`, `oxlint`),
  не LSP-демон: демон — это ещё один постоянный процесс ради того же текста.
- Потолок наивной версии: без git-репозитория диагностика не работает; повторный
  запуск чекера на неизменившихся файлах тратится зря.

## Демон (отложено)

**Steer — сделан целиком** (см. пункт 5 и `docs/subagents.md`). Канал сообщений живёт
вне цикла и вне TUI, в ящике сессии на диске; точка инъекции — граница хода (после записи
всех результатов шага и перед следующим запросом). Реализация от записи `Rec::Steer`
отличается только транспортом: вместо `mpsc` — файлы (`mail.rs`), поэтому steer работает
и между процессами (подагент↔родитель), чего `mpsc` не давал. Ввод во время хода прямо в
TUI сделан: readline в отдельном потоке, вывод через `ExternalPrinter` (`render::Sink`).

**Демон.** `snens daemon` держит открытые `Session` и гоняет цикл; транспорт — unix-сокет
`~/.local/share/snens/snens.sock` (Windows — named pipe, нужна tokio-фича `net`).
Протокол — JSON-строки, версия в первом кадре: клиент→ `send{session,text,source}`,
`subscribe`, `cancel`, `new`; демон→ `delta{kind:content|reasoning}`, `tool_call`,
`tool_result`, `usage`, `limit`, `done`, `error`. Тот же протокол обслуживает
Telegram/Discord/приложение. `tui` становится тонким клиентом (рендер Фазы 2 переезжает
туда). Рестарт демона не рвёт сессии: состояние на диске. Риск — протокол под одного
клиента (поэтому не раньше второй поверхности); первый шаг к нему уже сделан — ревью
уезжает отдельным процессом.

## Прочее

- Тулы написаны на Rust (workspace-члены `tools/<имя>`), собираются `snens build`,
  бинарник кладётся в `tools/<имя>/<имя>` и он в gitignore. Python из дефолтной
  установки исключён: на тонком устройстве интерпретатора может не быть.
- Тулы живут в репозитории харнесса; вынести каждый в свой репозиторий, когда
  появится ревью-цикл с issue на тул.

## Вложения (мультимодальность)

Сделано: канал вложений `SNENS_ATTACH_DIR` (свой каталог на вызов, env — сам факт
канала; команда, не знающая переменной, ничего туда не кладёт), нейтральная `Part`
(kind = image|audio|video|file) в `ToolResult.parts`, встроенный тул `view` кладёт
картинку в канал, проекция собирает `image_url` (base64, кеш по неизменному файлу),
элизия вложений по своему порогу `keep_attachments`. `attachments = false` выключает
канал и отправку.

Почему не встроенный `view` с полем `images`: это спецслучай на каждый тип медиа, а
`view` перестал бы быть обычным тулом. Нейтральный канал работает и для `run`
(скриншот кладёт файл обычной командой), и для будущих видео/аудио/документов —
без правки ядра. Картинки не гоняются через stdout: base64 портится капом вывода.

Осталось: мапинг audio/video/file в провайдерские форматы (сейчас отбрасываются
пометкой — ждём моделей, которые их понимают); приём вложения от человека
(`run --image`, `/img` в TUI); ресайз (внешний инструмент + `run`, в ядро картинные
крейты не тащим — размеры читаются из заголовка вручную).

## Компакция

Сделано: детерминированная элизия старых результатов тулов при выходе за `soft`,
журнал действий (`Ctx`) в логе, полные выводы обрезанных команд лежат в
`sessions/<id>.out/`. Не сделано: саммаризация на `hard` — элизия покрывает окно
в 1M, а саммари требует вызова модели и полезно только для маленьких окон.

Проверено синтетикой (окно 400 токенов, `seq 1 3000`): элизия срабатывает, проекция
уменьшается, структура сообщений не ломается (assistant с tool_calls всегда имеет
ответы), проекция детерминирована. Не проверено: поведение модели на урезанном
контексте — для этого нужна длинная живая сессия.

Инвариант проекции: ход, оборванный на середине (Ctrl+C, падение, убитый процесс),
оставляет в логе `assistant` с `tool_calls` без ответов, и провайдер такой запрос
отвергает. Достраивается в проекции, а не записью в лог: лог обязан остаться правдой,
а проекция — быть валидной при любом хвосте, откуда бы обрыв ни взялся.

## Платформы

Код платформенно-нейтральный: оболочка для `run` берётся из конфига (`shell`), PATH
детей склеивается через `join_paths` (разделитель свой у каждой ОС), имя бинарника — с
`EXE_SUFFIX`, каталоги данных — `APPDATA` на Windows и XDG на unix. Тулы компилируются
под `x86_64-pc-windows-gnu` и `aarch64-linux-android` (проверено `cargo check`, 0
предупреждений).

Осталось: `tools/selftest.sh` — единственное место на sh, для Windows его надо переписать
в `#[test]` внутри крейтов тулов (там `CARGO_BIN_EXE_<имя>` даёт путь к собранному
бинарнику на любой платформе). Харнесс целиком под Windows не проверен:
`cargo check --target x86_64-pc-windows-gnu` спотыкается на build-скрипте `ring` (TLS
reqwest) — нужен mingw, это ограничение тулчейна, а не кода.
