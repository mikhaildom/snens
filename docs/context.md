# Рабочий контекст

## Журнал и редактируемое зеркало

Исходный журнал сессии — append-only: сообщения, вызовы инструментов, результаты
и ревизии контекста остаются в нём для аудита. Уборка не переписывает журнал.
Рабочий контекст, отправляемый провайдеру, — отдельная редактируемая проекция.

Модель постоянно может читать и править зеркало `LIVE_CONTEXT.json` обычными
инструментами, затем применять изменения встроенным инструментом `ctx`:
`{"action":"commit"}` (пустой объект тоже означает commit). Действие
`{"action":"status"}` показывает состояние. Правка файла сама по себе ещё
не означает применение ревизии.

Уборка двухслойная.

**Автоэлизия** — детерминированный пред-шаг без участия модели: при переходе
через `context_budget` сами схлопываем самые старые результаты тулов в пометку
с именем тула, размером и хвостом команды (последние `keep_results` не трогаем),
пока оценка не опустится до `context_target`. Решение живёт записью `Rec::Ctx`
с картой заглушек `call_id -> пометка`; проекция накладывает её поверх, лог
неизменяем, уборка переживает resume и повторно не срабатывает на каждом ходу.
Полный результат остаётся в `sessions/<id>.out/` и в самом журнале.

**Правка зеркала моделью** — только если после элизии всё ещё выше цели. Тогда
на ходу уборки едет абзац «управляешь своим контекстом» (раньше он ехал всегда
и отвлекал модель на размышления о контексте вместо задачи), и модель правит
`LIVE_CONTEXT.json`. Это та же модель, что ведёт задачу, без отдельного summarizer.

### Хирургический доступ

Правка зеркала целыми блоками слишком груба: она возвращала агента назад и
теряла уже принятые решения и ответы. Поэтому есть инструмент `ctx`:

- `{"action":"clear","call_ids":["call_1"]}` — вырезать конкретные результаты;
- `{"action":"clear","before":"call_9"}` — всё строго до указанного;
- `{"action":"clear","keep_last":3}` — все старше N последних;
- маски `tool` и `min_bytes` сужают отбор.

`clear` трогает только результаты тулов — диалог (запросы пользователя и текст
ответов модели) неприкосновенен.

### Жёсткий запрет амнезии

`restore()` отвергает черновик, в котором удалён, изменён или переставлен любой
`user`-блок или assistant-текст: «cannot delete blocks containing user messages
or assistant text». Снять можно результаты тулов и аргументы вызовов — то есть
переваренное, а не ходы диалога. Это механическая защита от того, что уборка
вырезала целые куски и агент заново задавал уже решённые вопросы. Плата —
большую вставку пользователя нельзя ужать правкой зеркала; для этого заведён
отдельный механизм (крупное вложение уезжает файлом и отваливается с тулами).

Записка продолжения и новые заметки (`new-*`) добавляются как раньше; правило
«перед уборкой выписать принятые решения с пометкой РЕШЕНО» остаётся в промпте
уборки — жёсткий запрет не даёт потерять диалог, но не заменяет записку.

Вызов инструмента и его результат — атомарный блок: нельзя оставить вызов без
ответа или ответ без вызова. При нескольких вызовах в одном сообщении сохраняется
целостность всего блока с соответствующими результатами. Перед применением
проверяется корректность новой проекции; это валидация структуры, не защита от
prompt injection.

После успешного применения служебные пары `read`/`edit`/`write` именно зеркала
и `ctx commit` удаляются из эффективного контекста, но остаются в журнале.
Обычные вызовы инструментов сохраняются. Shell-правки через `run` автоматически
не классифицируются как обслуживание зеркала. Ошибка применения должна быть
видна модели; успешное применение подтверждается кратко, без повторной отправки
всего текста правки.

## Экономический бюджет и физическое окно

Размер окна модели и экономический бюджет — разные ограничения. Даже модель с
окном в миллион токенов не обязана получать весь накопленный контекст на каждом
ходе: это увеличивает стоимость API.

Настройки в корне `config.toml` (все величины — токены):

```toml
ctx_window = 1000000
context_budget = 0    # auto: 100k при окне <=300k, иначе 200k
context_reserve = 8192
context_target = 0    # auto: 70% эффективного бюджета
keep_results = 5      # сколько последних результатов автоэлизия не трогает

# профиль по модели: префикс slug, побеждает самый длинный
[models."vendor/model-with-cheap-cache"]
context_budget = 500000
context_target = 350000
```

- `context_budget > 0` задаёт экономический порог явно. При `0` окно до 300 000
  включительно даёт бюджет 100 000, большее окно — 200 000.
- `context_reserve` оставляет запас до физического предела для следующего хода.
  Эффективный запас — `min(context_reserve, ctx_window / 4)`: дефолт не обнуляет
  маленькие окна в синтетических тестах. Бюджет ограничен
  85% от `ctx_window.saturating_sub(эффективный запас)`, чтобы уборка была достижима до физического предела.
- `context_target > 0` задаёт цель после уборки явно, но не выше эффективного
  бюджета. При `0` цель — 70% эффективного бюджета с округлением вниз.
- `[models.<slug>]` задаёт пороги для конкретной модели: цена кеша у них разная,
  а значит и терпимый размер контекста. Побеждает самый длинный совпавший
  префикс. Явный `context_budget`/`context_target` сильнее профиля. Смена
  модели в рантайме меняет профиль на следующем ходу.
- `keep_results` — сколько последних результатов тулов не трогает автоэлизия.

По умолчанию окно 250k означает уборку около 100k с целью 70k; окно 1M — уборку
около 200k с целью 140k. Это экономические пороги, а не доли физического окна.
У модели с очень дешёвым кешем профиль ставит 500k/350k: ранняя уборка там стоит
дороже, чем большой контекст. Это пример настройки, а не дефолт.

При достижении бюджета сначала срабатывает автоэлизия (см. выше), и только если
её не хватило до цели — модель получает требование привести зеркало в порядок.
Повторное требование зависит от результата уборки и последующего роста (порог
поднимается на четверть бюджета), а не повторяется на каждом ходу.

Настройки `soft`, `hard`, `keep_attachments` больше не используются. Старые
конфиги с этими ключами читаются, но значения игнорируются.

Порог считается **по токенам провайдера**, а не по наивной оценке: сырая
эвристика `длина/3` помножается на откалиброванный множитель — отношение
`usage.prompt_tokens` к нашей оценке той же проекции (`est_tok` в записи
`Rec::Usage`), со свежими ходами в большем весе. Так оценка подстраивается под
реальный токенизатор модели и перестаёт завышать.

`/compact [инструкция]` в TUI запрашивает уборку тем же агентом.
Повторное напоминание после превышения бюджета приходит только после прироста
ещё на четверть бюджета; после снижения до target порог снова равен budget.
Напоминания сохраняют порог для resume. Оценка токенов приблизительная; деньги
и фактический размер запроса берутся из provider usage.

## Проверки

Unit/loop-тесты: несколько ревизий, >=40k контекста (loop ~80k), resume,
отказ malformed/stale/orphan drafts, смешанные tool-batches, сохранность вложений,
отдельные edit и commit шаги. Автоэлизия: свежие результаты защищены, повторный
план пуст (не срабатывает каждый ход), диалог и его решения остаются на проводе.
`ctx clear`: `keep_last`/`before`/`call_ids`/`min_bytes`, повторный вызов не
находит уже вырезанное. `restore()` отвергает удаление/правку user и assistant.
Калибровка: отношение usage/оценка, вес свежих ходов. Текстовая оценка не считает
base64 изображений; для изображения используется грубый резерв 4096 токенов.

Живые smoke-прогоны на `openai/gpt-6-luna`: shell-правка → отдельный ctx commit
→ принятая ревизия, точный маркер сохранён; проверен resume. Модель может повторно
вызывать commit и неверно интерпретировать статус: журнал и ContextRevision,
а не финальный отчёт модели, подтверждают применение. Измерения качества и полной
стоимости на задачах 100k–200k ещё не проводились.
