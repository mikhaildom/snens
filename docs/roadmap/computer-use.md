# Computer use: руки на машине пользователя

статус: не реализовано, план

## Зачем

Ядро часто живёт на машине без графики. Значит «руки» не могут быть частью ядра:
они стоят **на машине пользователя** и доступны ядру по сети. Это не обходной путь,
а форма продукта — у человека есть его Chrome, его логины, его IP, его GPU; три
вещи, которые нельзя арендовать.

Требования из кейса-эталона (заказ и доставка через внешние формы и аккаунты):
не занимать рабочий стол человека, переживать перезагрузку, будиться на события,
спрашивать разрешение на необратимое.

## Правило выбора пути

**Программное — всегда первым.** API, CDP, HTTP, файлы, шелл. Графический
интерфейс — крайний случай: он медленный, хрупкий (адреса живут до следующего
снимка, координаты ломаются от смены DPI) и дорогой по вниманию человека
(на время работы он теряет фокус).

GUI оправдан ровно в двух случаях: (а) у задачи нет программного интерфейса,
(б) сайт защищается от автоматизации и нужен **настоящий** браузер пользователя.

## Три уровня действий, в этом порядке

1. **CDP/HTTP** — если задача решается API или браузером, GUI не трогаем вообще.
2. **Дерево + адресные действия** — ARIA/AT-SPI/UIA/AX: снимок → ссылки (`e12`) →
   действие по ссылке. Дефолт для всего, где дерево есть.
3. **Пиксели** — скриншот + координатный клик: canvas, Electron без дерева, чужие
   приложения. Дорого и хрупко — только fallback.

Соло не работает ни одно представление: нужен цикл «снимок → адресное действие →
проверка». Снимок уходит **в файл**, в контекст — путь, число узлов, несколько
строк примера; ссылки валидны до следующего снимка; батч действий в одном вызове.

## Ограничения, с которыми придётся жить

- **Антибот.** Различают ровно три вещи: токен `HeadlessChrome` в UA,
  `pointer:fine`/`hover:hover` и размер экрана при `outerWidth==innerWidth`.
  Спуф WebGL-renderer'а запрещён — палец вниз через `failIfMajorPerformanceCaveat`.
  Палится не headless, а UA и GPU: **нужна машина с настоящим GPU**, сервер на
  llvmpipe для веба с антиботами бесполезен.
- **Рабочий стол.** Виртуальный дисплей и UIA/AX не изолируют: они живут в сессии
  человека, а `SendInput`/`CGEventPost` двигают физический курсор. Изоляция —
  отдельная сессия или своя среда.
- **Логины.** Не «новый пустой профиль» (там логинов нет) и не кража cookie.
  Легальных путей два: подключение к живому Chrome по согласию (тумблер
  `chrome://inspect/#remote-debugging`, Chrome 144+) или копия профиля
  `rsync --exclude 'Singleton*'` + `--user-data-dir` — снимок на момент копирования.
- **Профиль.** Тумблер отладки требует подтверждения на каждую сессию — для ночной
  работы неприемлемо. Свой `--user-data-dir` отдаёт CDP без подтверждений, значит
  профиль агента **отдельный** от профиля человека: логины вводятся один раз,
  цена — повторный вход, а не потеря проходимости.

## Решения, которые нужны до кода

1. Профиль браузера — свой (изоляция, логины вводятся внутрь) или подключаемся
   к живому Chrome пользователя (его логины, но согласие и доступ к jar)?
2. Чем «руки» говорят с ядром: HTTP или только `ssh host <verb>`? Второе проще
   и безопаснее, первое нужно для машины без ssh.
3. Долгие сценарии (`case`: `state.json` + `events.jsonl` + `deadline`) живут
   в ядре или на машине пользователя — зависит от того, чей это продукт: наш
   сервер как хост подписок или локальный агент как автономный.

Реализовано на сегодня: тонкие CLI-тулы «рук» (браузер по CDP и окна по
AT-SPI/UIA). Демона, установщика и долгих сценариев в дереве нет.
