# Computer use для snens: демон на машине пользователя

Дизайн-спека.

## Постановка

Ядро часто живёт на машине без графики (сервер, контейнер, VPS). Значит «руки» не могут
быть частью ядра — они должны стоять **на машине пользователя** и быть доступны ядру
по сети. Это не обходной путь, это форма продукта: у пользователя есть его Chrome, его
логины, его IP, его GPU — три вещи, которые нельзя арендовать.

Кейс-эталон (заказ и доставка через внешние формы и аккаунты): дни переписки, вход в
свои аккаунты, формы, оплата. Требования из него: не занимать рабочий стол человека,
переживать перезагрузку, будиться на события, спрашивать разрешение на необратимое.

## Правило выбора пути

**Программное — всегда первым.** API, CDP, HTTP, файлы, шелл. Графический интерфейс —
крайний случай: он медленный (371 мс на дерево против единиц мс на вызов API), хрупкий
(адреса живут до следующего снимка, координаты ломаются от смены DPI) и дорогой по
вниманию человека (на время работы он теряет фокус).

GUI оправдан ровно в двух случаях: (а) у задачи нет программного интерфейса,
(б) сайт защищается от автоматизации и нужен **настоящий** браузер пользователя.

## Три уровня действий, в этом порядке

1. **CDP/HTTP** — если задача решается API или браузером, GUI не трогаем вообще.
2. **Дерево + адресные действия** — ARIA/AT-SPI/UIA/AX: снимок → ссылки (`e12`) →
   действие по ссылке. Дефолт для всего, где дерево есть.
3. **Пиксели** — скриншот + координатный клик: canvas, Electron без дерева, чужие
   приложения. Дорого (~1036–1800 токенов на кадр 1024×768) и хрупко — только fallback.

Замеры, которые это обосновывают: сырое `Accessibility.getFullAXTree` — 505–626 КБ JSON
на страницу, сжатие по интерактивным узлам — 10–16 КБ (в 30–60× дешевле); OSWorld
a11y-only 2.4–12.2 % против screenshot-only 5.3–5.8 % — соло не работает ни одно
представление, работает цикл «снимок → адресное действие → проверка».

## Что делает демон `snensd`

Один статический бинарник (Rust, как тулы), без рантайма. Подсистемы:

| подсистема | Linux | macOS | Windows |
|---|---|---|---|
| `browser` | CDP к своему/пользовательскому Chrome | то же | то же |
| `ax` | AT-SPI2 по D-Bus (`GetAddress` работает по чистому ssh) | AX API | UI Automation |
| `input` | XTEST / libei-портал / uinput | `CGEventPostToPid` + AX-действия | `SendInput` + UIA-паттерны |
| `screen` | CDP `Page.captureScreenshot` / grim / X `GetImage` | ScreenCaptureKit | DXGI Desktop Duplication |

Интерфейсы:

- локально: `snensd <verb>` — тот же контракт, что у тулов (`--help`, argv, stdin);
- по сети: HTTP JSON на `127.0.0.1:7431` (по умолчанию только loopback), токен из файла;
- через ssh: ядро зовёт `ssh host snensd <verb>` — сетевой API не обязателен, ssh уже есть.

Установка «одним файлом»:

```sh
curl -fsSL https://…/snensd -o snensd && chmod +x snensd
./snensd install          # systemd --user / launchd / служба Windows + конфиг
./snensd doctor           # display, WM, a11y-шина, Chrome, права uinput, порт
```

`install` пишет `~/.config/snensd/config.toml` (профиль браузера, allowlist доменов,
политика аппрувов), включает автозапуск и `Restart=always`.

## Контракт тулов на стороне ядра

Два тонких CLI-тула, оба — клиенты демона, оба работают и без него (fallback: свой
Chrome по CDP). Никакого MCP: замеры — 1 365 против 44 026 токенов на задачу (32×),
114k против 27k у Playwright, и README самого Microsoft советует CLI.

**`web`** — браузер. Реализован в `tools/web` (P0), установка = один бинарник.

```
web connect [--port N]             # найти Chrome с тумблером в chrome://inspect
web open <url> [--new]             # перейти; печатает URL и title, дальше snap
web snap [--depth N]               # дерево в файл, адреса e1…eN → refs.json
web act --json '[{"click":"e3"},{"type":{"ref":"e1","text":"…"}},{"press":"Enter"}]'
web text [--limit N]               # видимый текст: дешевле дерева, когда нужен только текст
web eval '<js>'                    # проверка и извлечение
web shot [--full] [--out f.png]    # пиксели: canvas, верификация
web probe                          # ввод реально доставляется? (иначе клики молча в никуда)
web --host user@machine <любая команда>   # то же по ssh на машине пользователя
web connect --tunnel user@machine         # ssh -L к её Chrome: бинарник там НЕ нужен
web disconnect                            # закрыть туннель (Chrome не трогаем)
```

`--tunnel` — то, ради чего сначала и стоит всё: на машине пользователя ничего не
устанавливается, достаточно, чтобы в её Chrome был включён тумблер отладки. Мы
поднимаем `ssh -N -L <локальный>:127.0.0.1:<порт>` (отвязанный от терминала, pid в
состоянии) и говорим с её браузером как с локальным. Порт `Host` и ws-URL
переписываются на туннельный: Chrome на той стороне отвечает 403 на чужой `Host`.

Проверено на живом sshd (туннель к Chrome по ssh, тестовая страница логина): `connect` → `snap`
(61 узел, 3 адреса) → `act` (логин) → `/inventory.html` → `text`. Туннель переживает
процесс, `probe` через него видит доставку ввода, `disconnect` его снимает.

### Как человек заходит в профиль агента и видит его работу

Два разных вопроса, оба решены командами:

**Залогиниться в аккаунты.** Тот же профиль агента открывается как обычный Chrome —
человек логинится руками, дальше агент работает в нём уже залогиненным:

```
web launch --visible --tunnel user@machine     # откроется окно на экране пользователя
# человек логинится в свои аккаунты в этом окне, закрывать его не нужно
```

**Видеть, что делает агент.** `--visible` поднимает Chrome **в сессии пользователя**
(`schtasks /IT`), поэтому окно появляется на его мониторе; `web show` выводит его
на передний план. Без `--visible` процесс живёт в сессии 0 — служебной, без экрана:
CDP работает, окна нет.

Грабли, проверенные живьём (Windows):

- ssh всегда попадает в **сессию 0**. Chrome, запущенный оттуда, не имеет окна, и
  `MainWindowHandle` из ssh равен 0 даже когда окно есть — не путать с «окна нет».
  Смотреть `EnumWindows` изнутри сессии пользователя.
- Окно может открыться **на втором мониторе** (`x = -1910`): при съёмке экрана брать
  `SystemInformation.VirtualScreen`, а не `PrimaryScreen`.
- Кириллица в `.ps1`, переданном аргументом ssh, ломается; через stdin тоже не всегда —
  файл кладём только ASCII.

### Профиль: отдельный, и это решает автономию

Тумблер в `chrome://inspect/#remote-debugging` требует **Allow на каждую сессию** — для
ночной работы неприемлемо. Проверено на живом Chrome под Windows: с собственным
`--user-data-dir` Chrome отдаёт `/json/version` = 200 и полный CDP **без единого
подтверждения**, и такой процесс переживает ssh-сессию (обычный `Start-Process` из ssh
умирает вместе с ней — нужен `Win32_Process.Create`, на unix `setsid`).

Отсюда решение: **профиль агента отдельный от профиля человека**. Логины в него
вводятся один раз (или импортируются из своего профиля копией), риск «агент видит мои
cookie» снимается, автономия сохраняется.

```
web launch --tunnel user@machine [--port N] [--profile путь]
```

Одна команда: находит chrome.exe на той стороне, поднимает Chrome с отдельным профилем
**отвязанным от сессии процессом** (`Win32_Process.Create` на Windows, `setsid` на unix),
ждёт `200` на `/json/version` и подключает туннель. Повторный `launch` переиспользует
свой браузер (порт помнится в состоянии, владелец порта проверяется по командной строке)
— второй профиль не поднимается.

Грабли, проверенные живьём, а не вычитанные:

- `%USERNAME%` в `--user-data-dir` Chrome **не** раскрывает: каталог создался буквально
  с именем `%USERNAME%`. Путь строится на той стороне из `$env:USERPROFILE`.
- Переменную PowerShell нельзя подставить внутрь строки в одинарных кавычках: Chrome
  получил `--user-data-dir=$prof` буквально. Склейка только конкатенацией.
- Обычный `Start-Process` из ssh умирает вместе с сессией; `Win32_Process.Create` — нет.
- Занятый порт означает, что Chrome прилип к уже запущенному процессу с *чужим*
  профилем: порт проверяется до запуска, свободный подбирается сам.
Проверено: агентский профиль на свежем Chrome проходит `bot.sannysoft.com` без единого
failed (`webdriver=false`) и Cloudflare managed challenge — то есть цена
«отдельного профиля» — только повторный вход в аккаунты, а не потеря проходимости.

**Чем это отвечает на развилку.** Требование «подтверди Remote debug» относилось не к
CDP, а к *чужому* профилю: Chrome защищает профиль человека. Свой профиль — своя
воля, подтверждений нет. Значит автономное управление браузером реализуемо, и
выбирать надо не «тумблер против отдельного профиля», а «как один раз залогиниться в
профиль агента» — руками при настройке или копией профиля.

**Режим одобрения Chrome 144+ ломает три привычных вещи** (проверено на живом Chrome
под Windows через ssh-туннель), и тул их обходит:

| что | как ведёт себя | обход в `web` |
|---|---|---|
| HTTP `/json/list`, `/json/version` | 404 Not Found | вкладки через `Target.getTargets`, ws-путь из файла `DevToolsActivePort` на той стороне |
| ws вкладки напрямую | 403 Forbidden на рукопожатии | `Target.attachToTarget{flatten:true}` и все вызовы в сессии |
| `Host` в ws-рукопожатии | 403, если не совпадает с портом Chrome | подставляется `127.0.0.1:<порт на той стороне>` |

Заодно закрыт вопрос «палится ли мой браузер»: на настоящем Chrome пользователя
sannysoft не даёт ни одного failed, WebGL — настоящий GPU, `webdriver=false`;
Cloudflare managed challenge (nowsecure.nl) проходит без единого действия. Сравнение
с эмуляцией на сервере (llvmpipe) — это и есть цена «настоящей машины»: единственное,
что нельзя подделать.

Что дал живой прогон (страница логина, headless и headed под Xvfb):

- `snap` на странице логина: 61 узел AX, 3 интерактивных, вывод — 14 строк вместо
  дерева (файл отдельно). На каталоге — 227 узлов, 28 адресов.
- батч из 5 действий (клик, Control+a, Delete, ввод, вход) проходит одним вызовом
  и возвращает смену страницы: `страница сменилась: …/inventory.html`.
- **ввод CDP доставляется активной вкладке, а не той, чью сессию держим.** Клик по
  «своей» неактивной вкладке молча уходит в соседнюю. Поэтому `act` активирует
  вкладку (`Target.activateTarget` + `Page.bringToFront`), а `probe` проверяет
  фактом: считает события на странице после настоящего клика.
- в залипшем инстансе (десятки навигаций в одной вкладке) ввод может не доставляться
  вовсе, при `visibilityState=visible` — единственный признак это `probe`.
- AX-дерево обновляется асинхронно: сразу после навигации Chrome отдаёт дерево
  предыдущего документа при новом `location.href`. Поэтому `snap` снимает до
  совпадения двух подряд снимков, а `act` сравнивает URL и на смене страницы
  печатает сводку, а не «дельту» между разными документами.

**`desk`** — не браузер (тот же протокол, другое дерево):

```
desk apps                          # что запущено, с id приложений
desk snap --app <id>|--focus       # AT-SPI/UIA/AX-дерево в файл, ссылки n12
desk act --json '[{"press":"n7"},{"set":{"ref":"n9","text":"…"}}]'
desk shot [--app <id>]             # пиксели: fallback и верификация
desk key <combo> | desk type <text> | desk click <x> <y>
```

Правила, взятые из замеров (это и есть «качество/скорость/токены»):

- снимок уходит **в файл**, в контекст — путь, число узлов, 5 строк примера;
- ссылки (`e12`, `n7`) валидны до следующего снимка; `act` возвращает **дефф** нового
  состояния, а не полное дерево (Stagehand: дифф на втором шаге, кэш = 0 токенов);
- батч действий в одном вызове (Codex: persistent REPL ровно поэтому);
- `--delta` и фильтр по интерактивным ролям по умолчанию включены, полное дерево — флагом;
- успешный путь сохраняется **как скрипт** с проверкой предусловий и откатом в агента
  (Skyvern: $0.11 → $0.04, 2.8× по времени) — но не как «переиграть траекторию»:
  неверный закэшированный клик дороже медленного.

### Цепочки: один вызов вместо десяти

Узкое место было не в действии, а в том, что перед каждым кликом нужен `snap`
(дерево заново, 300–700 мс и 68 строк вывода). Решение — действовать **по селектору**,
не снимая дерево:

```json
[{"set_sel":{"aid":"view_1012","text":"https://example.com/"}},
 {"keys":"{ENTER}"},
 {"wait_sel":{"name":"Username","aid":"user-name","timeout_ms":15000}},
 {"set_sel":{"aid":"user-name","text":"standard_user"}},
 {"click_sel":{"aid":"login-button"}},
 {"wait_sel":{"name":"Products","timeout_ms":15000}}]
```

Замер: семь шагов (навигация + логин) — **3.1 с одним вызовом**; снапшот нужен один раз,
чтобы узнать `aid`. `wait_sel` — это условие готовности, а не пауза: срабатывал за 547 и
263 мс там, где `wait` ждал бы фиксированные секунды впустую.

Осталось: запись успешной цепочки в скрипт с
проверкой предусловий, `expect` у действия (проверка результата) и нормальная работа с
Win32-диалогами через `GetDlgItem`/`BM_CLICK` вместо координат.

## Окружение: не занимать рабочий стол

Из ресёрча: виртуальный дисплей и UIA/AX **не изолируют** — они живут в сессии
человека, а `SendInput`/`CGEventPost` двигают физический курсор. Изоляция = отдельная
сессия или своя среда. Практический порядок внедрения:

1. **Свой Chrome-профиль демона** (не рабочий стол человека вообще): CDP-действия
   физическую мышь не трогают. Закрывает 80 % задач, ноль риска для человека.
2. **Второй виртуальный дисплей** в той же сессии (Xvfb :99 / IDD / CGVirtualDisplay) —
   для приложений, которым нужен экран; на Linux проверено: Xvfb 40 МБ + openbox 9 МБ,
   headed под Xvfb ≈ headless по памяти (329 против 312 МБ).
3. **Отдельная сессия/машина** — только если человек прямо запрещает агенту свой стол:
   Windows — Hyper-V VM с GPU-P (20–25 ч/д), macOS — второй пользователь + auto-login
   (25–30 ч/д). В первый релиз не берём.

Логины пользователя: не «новый пустой профиль» (там логинов нет по определению) и не
кража cookies. Два легальных пути: (а) подключение к живому Chrome через согласие —
тумблер `chrome://inspect/#remote-debugging` (Chrome 144+), это же `--autoConnect`;
(б) копия профиля `rsync --exclude 'Singleton*'` + `--user-data-dir` — снимок на момент
копирования. Chrome ≥136 игнорирует `--remote-debugging-port` на дефолтном профиле.

## Антибот: что нельзя подделать

Проверено руками (свежий Chrome, Cloudflare managed challenge, sannysoft, creepjs):

- режимы различают ровно три вещи: токен `HeadlessChrome` в UA, `pointer:fine`/`hover:hover`
  и размер экрана при `outerWidth==innerWidth`; canvas/audio/плагины/`webdriver` — идентичны;
- **SwiftShader в WebGL renderer не лечится флагами** — красный всегда. Спуф renderer'а
  запрещён (палец вниз через `failIfMajorPerformanceCaveat`);
- headful под Xvfb с честным UA прошёл Cloudflare 3/3, headless с честным UA — тоже 3/3,
  а headful с `HeadlessChrome`-UA — 0/1. То есть палится не headless, а UA и GPU;
- вывод для продукта: **демон требует машину с настоящим GPU**. Сервер без GPU
  (llvmpipe) для веба с антиботами бесполезен, и облачный оффер тоже требует GPU-боксов.

## P2: окна вне браузера (`desk`)

Браузер — это `web` (CDP дешевле и точнее). `desk` — для всего, что вне него:
мессенджеры, файловые менеджеры, диалоги ОС, canvas.

**Устройство.** На машине пользователя работает долгий процесс-агент в **его**
интерактивной сессии; мы говорим с ним по одной JSON-строке на запрос через
ssh-туннель. Контракт тот же, что у `web`: `apps` → `snap` (дерево с адресами
`e1…eN` в файл) → `act --json '[...]'` батчем → `shot` для пикселей.

```
desk launch --tunnel user@machine      # поднять агента в сессии пользователя
desk apps                              # окна: индекс, заголовок, класс, pid, рамка
desk snap --window Chrome              # 133 узла, 85 адресов, 371 мс
desk act --window Chrome --json '[{"click":"e39"}]'
desk shot --window Chrome --out f.png  # 1440x900, скриншот конкретного окна
desk stop / status
```

**Замеры на живой машине** (Windows 11): перечислить окна 22–84 мс,
полное дерево окна 133 узла за 371 мс, найти элемент и нажать 88 мс. Проверено
действием: `click` по кнопке добавления в корзину через `InvokePattern` → счётчик
корзины изменился; результат сверен независимо через CDP.

**Почему агент, а не «запустить скрипт на вызов».** Из ssh мы попадаем в сессию 0,
где UI Automation видит **ноль окон** (проверено). Плюс запуск через `schtasks`
стоит ~900 мс против 371 мс на сам обход дерева.

Грабли, каждая проверена и закреплена в коде:

| что | симптом | лекарство |
|---|---|---|
| `.ps1` с кириллицей без BOM | `Unexpected token`, скрипт падает на кавычке | BOM + копирование `scp` (а не `echo`/`more`) |
| `cmd /c echo X >> f` | файл молча короче на ~900 байт | `scp`, байт в байт |
| `certutil -decode` на существующий файл | `ERROR_FILE_EXISTS`, код 80 | удалить цель перед декодированием |
| `StreamReader.ReadLine` на `GetStream` | клиент получает пустой ответ | читать байты и резать по `\n` самому |
| `%USERNAME%` в пути для `scp` | `dest open ... No such file or directory` | спросить `%USERPROFILE%` на той стороне |
| `netstat \| findstr :PORT` | TIME_WAIT считается «уже слушает», агент не стартует | проверять только `State=Listen` |
| рамка окна `Infinity` | `Cannot convert "∞" to Int32` | `Clamp-Int` с проверкой NaN/Infinity |
| действие как «первое поле кроме ref» | `click` считался пустым | искать известные имена действий по списку |
| адрес внутри значения действия | «адрес неизвестен» | принимать и `{"click":"e39"}`, и `{"ref":"e39",...}` |

**Границы.** Linux-агент (AT-SPI по D-Bus) ещё не написан — это следующий шаг, зато
проверено, что AT-SPI работает по чистому ssh без X. На macOS — AX API, тот же
контракт, но TCC требует ручного подтверждения.

## События и долгие сценарии

Кейс «дни переписки» не решается сессией агента: нужен `case` — `state.json` +
`events.jsonl` + `deadline`. Триггеры: почтовый `watch` (7 дней, продление повторным
`watch`, истина в `historyId` — push теряется при >1/с), IMAP IDLE (переоткрывать каждые
29 мин), Graph subscription (нужен HTTPS-эндпоинт). Формы без событий (PCBWay) — опрос.

Механика: watcher-процесс (`Restart=always`) + systemd timer на продление и дедлайны;
дедуп по `Message-ID`; backoff 2ч→6ч→24ч→72ч, дальше эскалация человеку, а не третье
письмо; «жду до вторника» — строка из `deadline`, не текст модели.

## Аппрувы

Опасное — оплата, отправка формы, удаление, sudo, ввод пароля — уходит в аппрув-хук
**до** действия: `act` с флагом `danger` требует токен из ядра или кнопку человеку.
Список разрешений — файл, не состояние сессии (Codex: per-app allowlist + объект
аппрува в транспорте). Демону не даём управлять собственным аппрув-UI.

## Порядок работ

| фаза | что | цена |
|---|---|---|
| P0 | `snensd` (browser + CDP + снапшот в файл + refs + батч), `web` как тул, `install`/`doctor`, Linux | 4–6 ч/д |
| P1 | подключение к живому Chrome (согласие) + копия профиля + headed на виртуальном дисплее | 3–4 ч/д |
| P2 | `desk`: AT-SPI + XTEST, Wayland-портал как второй бэкенд, `desk` тул | 5–7 ч/д |
| P3 | `case` + триггеры (почта, опрос форм, дедлайны) + аппрувы | 4–6 ч/д |
| P4 | macOS (AX + ScreenCaptureKit + TCC), Windows (UIA + DXGI) | 20–30 ч/д каждый |

## Решения, которые нужны до кода

1. Профиль браузера демона — свой (логины вводятся один раз внутрь него, полная
   изоляция) или подключаемся к живому Chrome пользователя (его логины, но согласие и
   полный доступ к jar)? Начинать надо с одного.
2. `snensd` общается с ядром по HTTP или только через `ssh host snensd …`? Второе проще
   и безопаснее, первое нужно для машины без ssh.
3. `case` живёт в ядре (сервер) или в демоне (машина пользователя)? Зависит от того,
   чей это продукт: наш сервер как хост подписок или локальный демон как автономный.
